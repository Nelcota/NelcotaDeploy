# Status

NelcotaDeploy has no production-approved release. The backend and web interface are implemented and tested locally. **Local verification is not VPS acceptance:** nothing below has been accepted on real servers, real devices, or with real third-party credentials. The [VPS acceptance guide](vps-testing.md) is the procedure for that, and its acceptance record is still empty.

## Verified locally

- Static builds of panel and agent (CGO disabled, trimpath, automatic PGO), including linux/arm64 cross-builds.
- `make build test lint check-generated` and the race detector. Generated Protobuf, sqlc, and web assets reproduce from a clean copy with protoc 36.1.
- Integration tests with real Docker, BuildKit v0.34.0, and Caddy v2.10.2: builds, hardened containers, healthchecks, route swaps under continuous short-request traffic without observed losses, rejection of unhealthy candidates, and cleanup of old containers and images.
- Installer syntax in Debian 12 and Ubuntu 22.04 containers. Root installation was not performed.
- Backup, offline restore, signed update, and executable rollback, including official Minisign interoperability and the local staging packages described in [staging releases](staging-releases.md).
- Browser tests in Chromium against `nelcota-panel dev` (simulated agents, metrics, and logs). Passkeys use Chromium's virtual authenticator; backend tests use a virtual ECDSA authenticator.
- GitHub API tests use simulated transport. S3 tests use local TLS and an official SigV4 vector. Notifications are tested against local HTTP and SMTP servers.
- govulncheck v1.9.0: no reachable or imported-package findings. One required-module warning remains for the unimported `golang.org/x/crypto/openpgp` ([GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932)).

What the GitHub workflows and release scripts have and have not run is listed in [development](development.md#verification-status).

## Requires real infrastructure or credentials

- Install, reboot, update, and roll back on disposable Debian/Ubuntu VPS instances with real systemd, IPv4/IPv6 firewall, WireGuard, cgroups, and SSH. `scripts/vps-acceptance.sh` automates part of this but has not run against Hetzner Cloud.
- Full recovery on a new VPS, including WireGuard peers restored with the separate backup key.
- A real GitHub App, public webhook, and check runs; production S3 credentials (R2, Backblaze, MinIO).
- Passkeys on real browsers and devices; Safari and Firefox.
- The interface against a VPS panel with real agents: live metrics and logs over WAN latency.
- Notification delivery to real Slack, Discord, and SMTP providers; SSH agent installation on a real VPS; the `latest` release pointer on a real mirror.
- Production signing identity, release mirror, and official signed releases.
- The [performance targets](system-plan.md#performance-targets) on representative hardware with Go and Node apps, long requests, streaming, crashes, full disks, and reboots.

## Known limitations

- Rollback rebuilds the previous commit; images are not retained.
- Browser log and event streams are ephemeral. A saturated consumer is disconnected and can miss lines; build logs reload the stored snapshot on reconnect. SSE IDs are not persisted.
- Metric charts start empty on each page load because samples are not stored as a time series.
- Operations (backups, updates) have no client event stream; the interface polls while jobs run.
- The audit page filters the newest 1,000 entries.
- The DNS check reports where a domain points; the panel does not know servers' public IPs, so it cannot judge whether the record is correct.
- Roles are installation-wide (admin, member); there are no per-app permissions.
- The internal CA is valid for five years and does not rotate automatically. Service certificates (three months) do.
- No PGO profile is committed; one must come from representative production data.
- `templ fmt` v0.3.1020 fails on these sources, so `.templ` formatting is not enforced.
- Planned for a later phase: pull request previews, scale-to-zero, Trivy scanning, and Litestream replication.

## Security boundaries

- Installers change firewall, SSH, Docker, systemd, and keys. Run them on disposable machines first and keep tested SSH access.
- The agent controls the Docker daemon, which gives it host-level authority. Container and protocol restrictions do not isolate a fully compromised host.
- Keep release-signing, CA, master, and backup keys private and separate. Losing the master key makes encrypted settings, environment values, and TOTP secrets unrecoverable. The backup key must live outside both the host and the bucket.
- The audit log is append-only through SQLite triggers, not against root editing the database file.
- `users:write` is highly privileged.
- Zero-downtime switching was tested with short requests only. Validate the five-second drain with long requests, streaming, crashes, and route-commit failures before relying on it.
- Diagnostics (pprof, flight recorder) bind only to a private interface; profiles are private operational data.
