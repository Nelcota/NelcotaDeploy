The review found gaps in authorization, remote execution, backups and preview lifecycle handling and added regression coverage. The approved architecture changes isolate the panel and selected project networks in PR #37 and reconcile pull request previews in PR #35.

## Priority findings

### High Legacy workloads shared a Docker network with the control plane

The original Compose stack put the web panel, Traefik and the worker on `nelcota`. PR #37 moves the web panel onto a control-plane bridge and routes to its private address through the file provider. Docker socket access stays with the worker. Selected projects get separate bridges, and existing databases retain their legacy attachments during migration. The remaining rollout work is selecting and validating canaries on the panel and SSH hosts. [Production stack](../docker-compose.yml) · [Network rollout](network-isolation.md) · [PR #37](https://github.com/Nelcota/NelcotaDeploy/pull/37)

### High Out-of-order GitHub events could restore stale preview state

GitHub can deliver events out of order. A late `synchronize` previously reopened a closed preview. PR #35 persists a reconciliation request with each signed delivery and fetches the authoritative state in the worker. A lease and delivery-generation check fence stale responses. The worker rechecks active previews it has reconciled to recover missed closures. New heads cancel earlier webhook deploys, and a failed attempt with a live lease can restore the prior route of a still-active preview. Closed previews use the durable cleanup job. An already-running proxy write can briefly disagree with SQLite, and a process killed mid-write relies on durable cleanup or the next deployment. [GitHub delivery ordering](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/troubleshooting-webhooks#webhooks-deliveries-are-out-of-order) · [PR #35](https://github.com/Nelcota/NelcotaDeploy/pull/35)

## Architecture proposal

Keep one deployable application with the web and worker running as separate processes. Organize business capabilities as packages with a narrow public API. Keep HTTP parsing, authorization and response mapping at the web boundary. Keep deployment transitions and preview policy in their owning packages. Give the worker responsibility for external side effects and retries. SQLite remains the source of truth for job state and reconciliation intents.

1. **Enforce package boundaries.** Direct cross-package imports through each capability's public entry point. Extract a dependency seam where there are multiple actual implementations or an integration boundary that needs a controllable test double. Consolidate shared state transitions into the package that owns the invariant. Use Strategy for local and SSH execution where behavior varies, and keep simple conversions as functions.
2. **Separate the control plane from project networks.** The approved topology moves the panel and proxy to a control-plane bridge and delegates Docker operations to the worker. Use the documented per-project canary and rollback steps to validate routes, database reachability and legacy bridge compatibility before broadening deployment. [Network rollout](network-isolation.md)
3. **Reconcile external state durably.** Persist webhook reconciliation requests alongside deliveries. Keep retries, periodic checks and lease fencing in the worker. The implementation adds GitHub API traffic and eventually consistent preview updates in exchange for convergence when webhook events arrive late or are missed.
4. **Scale from measured constraints.** Watch queue age, SQLite lock latency, webhook rate limits, container start time and backup throughput. Add a shared abuse-control budget when the panel gains multiple replicas. Revisit external queue or database options when production measurements show contention that indexing and bounded concurrency cannot address.
